# Shopify read-only synchronization

## Setup

Connect a Shopify store through `PUT /settings/integrations` using an HTTPS `*.myshopify.com` domain and the Admin API access token. This endpoint is owner-only. Tokens are read from the selected business's settings; synchronization requests do not accept a store host or credential. The token is never included in responses or error summaries.

Grant only the scopes needed by the configured store/app:

- `read_products` for product and variant data.
- `read_inventory` for variant inventory quantities.
- `read_orders` for order and line-item data.
- Shopify may require `read_all_orders` to access orders older than its standard recent-order window; otherwise the initial order sync is limited by the access Shopify grants.

Use `GET /shopify/status` to check connection status. Use `POST /shopify/sync/products`, `POST /shopify/sync/orders`, or `POST /shopify/sync` to retrieve records. Requests require a bearer token and `X-Business-ID`; every read and write is scoped to the authenticated membership. `GET /shopify/sync/history` returns the selected business's runs and safe counts/errors.

## Sync behavior and source of truth

The client reads `SHOPIFY_API_VERSION` from application configuration (default `2026-04`; use a currently supported quarterly version) and makes HTTPS GET requests only. It follows validated cursor links on the configured store host, disables redirects, uses bounded timeouts and retries, and handles throttling. Shopify identifies variants, orders, and line items by provider IDs; SKU is descriptive only and may be missing or duplicated. If a Shopify SKU conflicts with an existing SKU, its value is retained in `shopify_sku`, while the unique Norfae `sku` field is left unset for the conflicting variant.

Shopify owns product/variant title, category/type, description, vendor, status, image URL, price, compare-at price, stock quantity, order identity/name and timestamps, order totals/status/refund total, city/province when present, and order line quantities/prices/discounts. `shopify_original_total_price` stores Shopify `total_price` (fallback: current total); `shopify_total_price` and `orders.selling_price` store `current_total_price` (fallback: original total). Thus Norfae retains the provider's original/current totals separately where both are supplied. Current total already reflects Shopify's current order state; successful refund transaction amounts are stored in `shopify_total_refunded` as a separate informational summary and are never subtracted from current total again. Pending/failed refund transactions are not included. Subtotal, total discounts, tax and summed shipping-line prices remain separate provider-reported fields; Norfae does not recompute current total from those components. Line item `total_price` is quantity times line unit price less Shopify's line `total_discount`, floored at zero. Refunds are not allocated to line items and are not imported as separate Norfae ledger rows. Norfae owns buying/product cost, packaging and delivery costs, and manual financial adjustments. Synchronization does not overwrite these costs. A missing local product/variant leaves the line item unlinked and its cost unknown; no SKU or product identity is fabricated. The sync does not store customer name, phone, email, or street address. It requests the shipping-address object only to extract city and province. Product image URLs are stored only for HTTPS Shopify CDN hosts.

Orders with Shopify fulfillment `fulfilled` are labeled `FULFILLED`, not `DELIVERED`: fulfillment does not establish last-mile delivery. Canceled orders are `CANCELLED`; partial fulfillment is `PARTIALLY_FULFILLED`; refunded and partially refunded financial states are `REFUNDED` and `PARTIALLY_REFUNDED`. Norfae's profitability and intelligence aggregations include only `DELIVERED` orders, so all these Shopify statuses are excluded. This is a status filter, not a refund calculation: refund amount, recovered inventory/cost, and realized profit for refunded orders remain unavailable. In the deterministic profitability API, recognized revenue for delivered orders is the recorded `orders.selling_price`; gross revenue before discounts, refunds and net revenue after them cannot be certified from that formula. Product contribution uses delivered `order_items.total_price` less recorded item cost; discounts are reflected at line level, while refund allocation is not. Legacy analytics labels its delivered-order `selling_price` sum as both gross and net revenue; those labels are not a gross/net reconciliation. These definitions deliberately leave refund impacts unknown instead of deriving an unsupported formula. Archived/draft products are synchronized with their status; missing records are never deleted.

Initial syncs fetch the provider's accessible history. Later syncs use `updated_at_min` with a five-minute overlap. A run advances its timestamp checkpoint only when every fetched record validates. Invalid records are skipped with `partially_completed`, and the cursor stays put so a later run retries that window. Provider pagination/network failures make the run fail without committing catalog/order changes. Upserts and sync history are tenant-scoped; external identity unique constraints make repeated writes idempotent. PostgreSQL row locks serialize store binding, while resource running leases prevent duplicate active syncs and expire after one hour if a process stops unexpectedly. Store URL changes are rejected while a sync is running and after any completed or partially completed sync; token rotation for the same store remains available. A failed initial connection may be corrected before any successful sync. Reconnecting a different store requires an operator-reviewed data reset that removes only that business's imported Shopify products, orders, line items, sync history/cursors and associated references, with a backup and explicit confirmation; no automatic reset endpoint is provided. Do not switch stores by changing credentials alone.

## Swagger

In `/docs`, configure the integration, authorize with the owner bearer token, and set `X-Business-ID`. Call `/shopify/status`, then invoke a product or order sync. A full sync creates an aggregate run plus product and order run records. Review counts and safe error summaries at `/shopify/sync/history`. No endpoint creates or modifies Shopify data.

## Limitations

Shopify's REST Admin API is designated legacy for new integrations; this implementation follows the existing codebase's REST client and version rather than changing the integration architecture to GraphQL in this phase. The official REST guides describe cursor pagination and `429`/`Retry-After` behavior: [pagination](https://shopify.dev/docs/api/admin-rest/usage/pagination) and [rate limits](https://shopify.dev/docs/api/admin-rest/usage/rate-limits). The client cannot derive delivered status, shipping carrier cost, or product cost from these records. It does not sync customer PII, fulfillments as separate entities, refund transactions as separate ledger rows, or deleted-product tombstones.
